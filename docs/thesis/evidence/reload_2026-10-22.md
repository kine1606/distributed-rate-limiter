# Evidence: rule reload on SIGHUP under load (2026-10-22)

The Week 5 item: "a bad config file is rejected and the old rules stay live"
(`docs/THESIS_PLAN.md`); the module's acceptance test: "reload under load with zero failed requests"
(`src/config/README.md`).

## Design in one paragraph

The engines assume their rule table never changes: a lease holds a reference to its rule, and
callbacks keep references into the table. A reload therefore does not edit rules in place. It
parses the whole file (a file that does not load leaves the old rules live), builds a new engine
from it, and switches the gRPC service to it with one atomic pointer store. Checks from then on use
the new engine; a check already inside the old one finishes there. One second later the old engine
gives its unused leased tokens back to Redis, as at shutdown. The old engine is kept until the
process exits, so no check can meet a freed engine. Metrics keep their series across a reload; a
rule added by the reload gets its own. The signal handler only sets a flag, which the main loop reads
every 100 ms.

## A. Reload under load

**Setup.** `bench/reload_under_load.sh`: one limiter (engine `leased`, defaults) on the development
cluster, re-seeded before each pass, and `bench/loadgen` open loop at 10,000 checks/s on
`api_default` (10,000 keys, 12 connections, 2 s warm-up, 24 s measured). In each reload pass the
rules file is changed three times, each followed by `kill -HUP`. A probe (one key, one call at a
time for 1 s, on the rule `reload_probe`) shows which rules are live. Each run also has a control
pass: the same load with no reload. Laptop, 3 runs.

| Step | Probe on `reload_probe` (runs 1, 2, 3) | Expected |
| --- | --- | --- |
| before any reload | 3,513, 3,499, 3,491 calls, all `INVALID_ARGUMENT` | the rule does not exist |
| reload 1: rule added, bucket of 5, 1 a second | 5 of 4,011, 5 of 3,828, 5 of 3,863 allowed | about 5 allowed in 1 s |
| reload 2: bucket raised to 100,000, 100,000 a second | 3,782 of 3,782, 4,068 of 4,068, 4,155 of 4,155 allowed | every call allowed |
| reload 3: a file with an unknown algorithm | every call still allowed (3,619, 4,034, 4,149); logged `reload: cannot load rules from ...: rule 'broken': unknown algorithm 'no_such_algorithm'; the old rules stay live` | rejected, the rules of reload 2 stay live |

Main load, per pass (each sent its full rate; none skipped):

| Pass | Calls | Failed | p50 | p99 | p999 |
| --- | --- | --- | --- | --- | --- |
| control, no reload | 240,000 × 3 | 0 | 0.25 ms (0.25 to 0.26) | 0.72 ms (0.69 to 0.79) | 1.45 ms (1.33 to 1.96) |
| three reloads in 24 s | 240,000 × 3 | **0** | 0.30 ms (0.30 to 0.32) | 1.33 ms (1.27 to 1.39) | 3.44 ms (3.16 to 3.60) |

Medians of 3 runs, range in brackets.

- **No call failed** during 9 reloads (6 applied, 3 rejected), and every change was live at the
  next probe, 4 s after the signal.
- **What a reload costs**: p99 rose from 0.72 to 1.33 ms over a 24 s pass with three reloads. The new
  engine starts with no leases, so for about a second (at 1 call per key per second here) each
  key's first check waits for one Redis refill. The old engine's return of unused tokens runs at the
  same time: about 943,000 tokens from about 9,930 leases per reload, with no failed return.
- **Accuracy during the switch**: for the second before the old engine returns its tokens, both
  engines can hold a lease on the same key, so this instance can briefly take up to one extra chunk
  per key from Redis. That is stricter, not looser: other instances see those tokens as used until
  they come back.

## B. The cost on every check

The service now loads the engine pointer with an atomic acquire load (a plain load on x86-64)
instead of reading a `shared_ptr`. Measured old binary against new, alternating, 8 runs each,
closed loop (12 connections, 16 calls in flight each, 10,000 keys, 10 s):

| Engine | Before, median (range) | After, median (range) |
| --- | --- | --- |
| `allow_all` (the service alone) | 63,366 checks/s (59,237 to 74,645) | 63,681 checks/s (53,031 to 70,899) |
| `leased` | 62,110 checks/s (53,360 to 70,019) | 62,218 checks/s (58,289 to 70,741) |

No difference beyond run-to-run noise, which was large today: the same leased load measured 75,652
checks/s (74,930 to 75,936) on 2026-10-19 (`ceiling_and_envoy_2026-10-19.md`). These numbers compare
the two binaries with each other, not with earlier sessions.

## Limits

- A replaced engine's memory is kept until exit (about 8 MB of lease table, plus its leases).
  Restart a process that has been reloaded hundreds of times.
- Leased quota units in the old engine are not returned (at most one chunk, 0.1% of a day, per
  customer), as at shutdown.
- Usage events, the deny cache and the plan cache are shared by both engines, so a reload neither
  loses nor repeats them.
- One laptop, one limiter instance, 3 runs. Raw output: `results/2026-10-22_reload/` (git-ignored).
