# Evidence: where the server's CPU goes (Week 7 profile, 2026-10-24)

Script: `bench/profile.sh`.
- **Build:** the release server built again with frame pointers (`build/profile`). Ubuntu 24.04's
  libraries keep their frame pointers, so stacks are whole through gRPC and protobuf.
- **Sampling:** `perf record -F 999 --call-graph fp -e cpu-clock:u` for 10 s, under the closed loop
  (12 × 16 in flight, Zipf keys), one instance, pinned as in the matrix.
- **User space only** (`perf_event_paranoid` 2), so kernel time is missing from the shares.
- **Output:** flamegraphs in `docs/thesis/figures/profile_leased.svg` and `profile_customer.svg`;
  categories by `tools/profile_summary.py`; callers of allocation by a grouping over the folded stacks.

| Self time by category (leaf function) | Leased `api_default` (75,289 checks/s) | Customer rule (39,933) |
| --- | --- | --- |
| gRPC (core, C++, abseil) | 53.3% | 39.6% |
| allocation (malloc, free, new, delete) | 15.9% | 20.3% |
| other (libc, TLS, clock, unresolved) | 12.6% | 16.1% |
| locks and atomics (gRPC's) | 6.0% | 4.5% |
| Redis client (redis-plus-plus, hiredis) | 4.3% | 8.6% |
| the rate limiter's own code | 4.1% | 6.3% |
| memcpy and strings | 1.9% | 3.1% |
| protobuf | 1.9% | 1.4% |

Samples with a rate limiter frame on the stack: 44% (leased), 55% (customer). Callbacks run
inside the engine and finish the gRPC calls, so they count gRPC's work as well.

## Reading

- **The limiter's own code is 4 to 6% of the CPU.** gRPC takes 40 to 53%, plus most of the
  allocation and all the locks.
  - *What would help:* fewer gRPC calls per check, which `CheckBatch` already offers, or a lighter
    transport.
  - *What would not:* tuning the engine.
- **Allocation is 16 to 20%, spread thin.** The largest single caller is gRPC's per-call arena
  (2.8%), then gRPC byte buffers and status objects, then the Redis client's command formatting
  (`fmt::evalsha`, hiredis `sds`; 1.1 to 2.6% on the customer path). This project's own code
  allocates about 3% of samples on the customer path: lambda captures and `std::function` across
  the plan, burst and quota steps, the script's argument vector, and the call state. On the lease
  path it allocates nothing beyond gRPC's own.
- **No fix inside the project's code could move throughput past the run-to-run noise** (±5%).
  Yesterday's one large finding, abseil's deadlock detection (+24.5%), came from this kind of profile
  and is already in. What remains are allocator and build settings, measured below.

## Allocator and build settings, measured

`bench/ab_compare.sh` (release against the variant, 5 alternating runs, the two workloads above).
The run-to-run ranges were wide in this session: one baseline run fell to 43,554 checks/s.

| Variant | Leased `api_default` | Customer rule | Verdict |
| --- | --- | --- | --- |
| LTO (`-DCMAKE_INTERPROCEDURAL_OPTIMIZATION=ON`, `build/lto`) | 66,777 → 65,602 (−1.8%) | 40,036 → 37,851 (−5.5%) | noise, ranges overlap; not adopted |
| glibc thread cache 64 entries (`GLIBC_TUNABLES=glibc.malloc.tcache_count=64`) | 63,298 → 61,105 (−3.5%) | 36,562 → 34,837 (−4.7%) | noise, ranges overlap; not adopted |
| jemalloc (`LD_PRELOAD`, measured 2026-10-23) | unchanged | +3.7% | small; not adopted |

**PGO was not tried, for the same reason LTO gained nothing.** It rebuilds only this project's code,
4 to 6% of the CPU, so even a perfect result would stay below the noise. gRPC, glibc and the Redis
client come from Ubuntu's packages and are not rebuilt.
